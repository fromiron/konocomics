고정 채팅을 재사용하며 일회성 `codex exec`·앱 채팅의 CLI resume로 대체하지 않는다. 독립적인 작품·출처 조사에는 범위와 반환 근거를 지정해 서브에이전트를 사용할 수 있다. 원문 결속과 최종 판정은 고정 세션이 맡고 공유 DB·registry·STATE·발행은 병렬 위임하지 않는다. 일반 배치에서는 `--allow-model`, `--retry-model`, `--model-session`을 사용하지 않는다. `SOL_COMPLETE` 등 과거 이름만으로 모델을 추정하지 않는다. SWE-2 사용안은 폐기됐다.

## 4. 남은 작품을 나누는 방법

1. 조정자가 최신 canonical과 candidate·registry·기존 배정·완료 결과를 한 번 결합한다. 어느 쪽에서든 이미 유효하게 eligible인 작품, 아직 발행만 안 된 유효 PASS, 다른 활성 배정의 작품을 새 판정 목록에서 제외한다. 미발행 PASS는 발행 복구 목록으로 분리한다.
2. 현재 libraryOnly 수 1,483은 참고 snapshot이다. HOLD와 중복되므로 더하지 않는다. 실제 배정 수는 재계산한다. 정확히 1,483개가 남는다면 100개씩 14묶음과 83개 1묶음이지만 모든 HOLD를 자동 재판정하지 않는다.
3. 자료 상태로 구분한다: 원문·receipt 충분 / 제공 URL 추가 확인 / 서지·scope 등 구체적 gap / 검색 제한 때문에 조기 종료한 HOLD / 접근·근거 소진 HOLD. 앞의 네 부류를 예상 작업량에 따라 가용한 루나1~6 방에 고르게 배분한다. 장르·분량·기존 coverage도 함께 남겨 쉬운 작품 편중을 비교에서 식별한다.
4. 정상 HOLD를 점수만 올리려고 재판정하지 않는다. 과거 횟수 제한으로 탐색을 중단했고 구체적 미확인 출처 경로가 남았다면 **추가 수집 대상**으로 편입할 수 있다. 새 근거 확보 전에 같은 판정만 반복하지 않는다. 출처를 이미 소진한 HOLD는 새 출처·접근 변화·확인된 오류가 있을 때 재개한다.
5. 각 묶음에 batchId, ownerThreadId, parentThreadId, 코드/계약 버전, 기준 DB/registry SHA, workId 목록과 각 작품 brief·prior/HOLD·원문/receipt·리드 경로·SHA를 결속한다. 목록은 작은 인덱스이고 원문은 해당 작품에 도달했을 때만 읽는다.
6. 그룹 간 workId 교집합은 0이어야 한다. 중복 배정은 기존 작품 잠금에서도 거부한다. 재배정은 완료·중단 확인 후 미완료 항목만 새 소유자로 넘기고 기존 이력을 보존한다.

2026-09-21 초기 물량은 최대 3×100작품이었다. 앞으로 신규 물량은 가용한 루나1~6 방마다 최대 50작품이다. 모든 방이 끝날 때까지 기다리지 않고 **한 방의 배치가 끝나면 그 배치부터 확인·발행**한다. 마지막 50개 미만 묶음도 같은 절차를 사용한다. 완료는 배정한 작품 각각에 결과가 남았다는 뜻이며 PASS 목표가 아니다.

## 5. 검색 횟수 제한을 종료 조건으로 교체

기존 ‘추가 검색 1회·쿼리 2개’ 상한은 새 수집부터 폐지한다. 조정자의 재배정 없이 같은 세션이 필요한 추가 조사를 수행한다. 검색 횟수 대신 **남은 구체적 gap과 다음 탐색에서 새 정보를 얻을 가능성**으로 계속할지 판단한다.

- 기존 유효 raw/receipt → 제공 URL 원문 → gap에 맞는 추가 출처 순서로 조사한다. 이미 보존된 정상 응답을 다시 요청하지 않는다.
- 다음 검색의 목적을 기존 gap 메모에 짧게 남긴다. 정확한 권·ISBN의 공식 페이지, 특정 서사 관찰이 있는 장문 리뷰처럼 확인할 항목을 구체화한다.
- 새 독립 관찰·서지 확인·반대 근거를 얻고 있으면 계속한다. 새 정보량은 모델이 판단하며 쿼리 수나 URL 수로 적격성을 대신하지 않는다.
- 필수 사실 gap이 해결되면 바로 종료한다. known 축 최대화·전권 독해·이번 범위에서 제외된 Art·더 좋은 리뷰·기존 URL 목록 소진을 위한 조사 연장은 하지 않는다.
- 같은 내용·동일 원문 전재만 반복되거나 접근 가능한 관련 경로를 소진했으면 HOLD와 재개 조건을 남긴다. 횟수를 채우기 위한 검색이나 성과 없는 무기한 루프는 하지 않는다. 인증·차단 우회나 유료 서비스 신규 결제는 하지 않는다.
- 검색이 길어져도 실제 새 정보가 생기는 작품은 ‘느리다’는 이유만으로 HOLD로 바꾸지 않는다. 사용자 시간 제한·쿼터·시스템 중단으로 멈추면 근거 부족과 구분한 중단 상태를 남긴다. 장기 작업 상태는 로컬 checkpoint로 보존한다.
- 동결 후 새 근거가 필요해지면 기존 입력·판정을 보존하고 새 research revision을 저장한 뒤 새 입력으로 동결한다. 새 입력에서 영향받는 claim을 판정하고 전체 결과의 기존 기계 검사를 통과시킨다. frozen 파일 수정이나 다른 버전의 수치 합산은 금지한다.

원문이 적다는 이유로 자동 unknown을 만들거나, 탐색을 많이 했다는 이유로 accepted를 만들지 않는다. unknown≠0, 낮은 앵커, 실제 readingScope, 이번 범위에서 제외된 Art, 기존 prior·safety·coverage 계약은 그대로다.

## 6. 작업자 실행과 중간 저장

목표 흐름:

```text
조정자: 목록·기준·brief를 한 번 배정
  └─ 루나1~6: 세션별 목록 전체 수집 → 저장·동결 → 작품별 판정·비발행 검사 → checkpoint
한 세션의 현재 배치 완료 → 배치 receipt·요약 통지
조정자: 집계·예외 확인 → PASS 직렬 발행 → 제품 readback·백업
루나: 현재 배치 판정·CHECKED·요약·백업·완료 통지 → 예약된 다음 비중복 50작품 수집
```

- 수집→동결→판정은 같은 세션이 기존 helper를 호출해 이어간다. 정상적인 작품마다 조정자의 응답을 기다리지 않는다.
- 작품마다 코드가 구조·입력 결속·출처·scope·safety·coverage·HOLD 또는 봉인 결과를 검사한다. **기계 검사를 배치 끝까지 미루지 않는다.** 그래야 동일 형식 오류가 전체 작품에 반복되지 않는다.
- 비발행 상태는 `READY_FOR_PUBLICATION`, `HOLD`, `ERROR`로 구분한다. 이 상태명과 배치 receipt는 구현할 계약이며 아직 runner CLI에 존재하지 않는다. `FINISHED.status=VERIFIED`와 혼용하지 않는다.
- 한 작품의 원본·판정·검사·오류를 저장·백업한 뒤 그 작품 checkpoint를 완료로 기록한다. 배치가 끝날 때까지 결과를 메모리나 `.tmp`에만 보관하지 않는다. 작업 DB/백업은 기존 잠금 아래 짧게 쓰고 모델·네트워크 대기 동안 공유 잠금을 잡지 않는다.
- 아티팩트는 배치/작품별 고유 디렉터리에 둔다. 새 세션/턴에서 재개할 때 목록·checkpoint와 현재 작품만 읽는다. 배치 전체 raw나 전체 STATE·과거 대화를 매번 다시 읽지 않는다.
- 스키마·scope 오류는 해당 작품 안에서 같은 원문으로 국소 수정한다. 여러 작품에 걸친 공통 validator·manifest·저장 결함은 원본 오류를 보존해 조정자에게 즉시 알리고 의존 작업을 중단한다. 불량 결과를 배치 끝까지 쌓아 보고하지 않는다.

## 7. 조정자의 배치 확인과 발행

정상 완료 통지는 배치당 한 번 보낸다. 조정자는 개별 파일을 대화에 다시 출력하지 않고, 기존 validator가 만든 작품별 receipt를 집계해 다음을 확인한다.

1. 배정 ID·작품 집합·결과 경로·최종 SHA·입력 버전·owner가 일치하는가. READY + HOLD + ERROR가 배정 수와 일치하며 누락/중복은 없는가.
2. 모든 READY에 유효한 독립 판정·봉인·저장 receipt가 있는가. HOLD와 오류는 실제 이유·재개 조건으로 구분됐는가.
3. 공통 오류·의심되는 수치/출처 변화·유난히 반복되는 근거 문구 등 구체적인 의미 예외가 있는가. PASS율·confidence만으로 재심사하지 않는다.
4. 첫 배치군에서는 각 세션의 PASS 1건·HOLD 1건(존재하는 경우)을 원문→앵커→scope에 대조한다. 초기 품질 표본이며 전량 재판정이나 매 배치의 의무 이중 심사로 확대하지 않는다. 이후에는 확인된 이상 징후만 검토한다. 명백한 오류가 있으면 영향 범위를 식별해 해당 결과의 발행을 보류하고 독립적으로 유효한 결과는 진행한다.
5. READY 결과를 **최신 candidate/registry에 순서대로 적용**한다. 오래된 배치 기준 DB를 통째로 덮어쓰지 않는다. frozen 기준은 입력 provenance로 보존하고 최신 기준과의 충돌은 기존 rebase/conflict 경로로 처리한다. 다른 작품의 정상 변경 때문에 모델을 다시 호출하지 않는다.
6. 기존 Gold·서지·팩터·안전성·coverage·추천 엔진·제품 readback·backup 게이트를 통과한 결과만 VERIFIED다. 사용자 지정 ‘100개 후 승격’은 batch 확인 주기이며 SQL 한 트랜잭션/전체 100개 all-or-nothing 발행을 요구하지 않는다.

일부 HOLD/ERROR 때문에 유효 PASS 전체를 보류하지 않는다. 발행 중 오류가 나면 적용된 작품·before/after SHA를 기록해 그 지점에서 안전하게 이어간다. 공통 데이터 무결성 문제가 확인되면 같은 경계에 의존하는 발행을 멈춘다. 재실행은 결과·DB readback부터 하며 완료된 판정·발행을 다시 하지 않는다.

canonical `data/source/catalog.sqlite` 반영과 GitHub·배포 권한은 구분한다. 기본 배치 목표는 승인된 로컬 후보 승격이며 canonical 반영은 당시 사용자 승인 범위에서 기존 발행 경로로 별도 수행한다. ‘READY’나 후보 발행을 실제 제품 canonical 반영으로 보고하지 않는다.

## 8. 구현 순서 — 기존 경로를 확장

### P0. 발행 경계 오류와 알려진 실패 복구

- 대상: `scripts/catalog_authoring/legacy/followup-panel-tools/publish_authorized_followup.py`의 Gold alias 경계, 이를 호출하는 기존 publish 경로와 테스트.
- 실제 결함: canonical에 승인된 v4 alias 20개가 이미 반영됐는데 `candidate - canonical`이 매번 20개여야 한다고 요구한다. 이후 정상 발행에서 delta=0이 돼 실패한다.
- 수정: 승인 원장 자체의 정확성·Gold 원본 보존·현재 canonical alias 보존·허용된 추가 집합을 각각 검증한다. 신규 delta는 승인 집합 중 canonical에 아직 없는 항목과 일치해야 한다. 신규 20개인 첫 적용, 이미 적용된 0개, 일부 적용 상태를 구별하되 승인 alias 누락·무단 추가·삭제는 거부한다. 단순 `20 → 0` 변경이나 검사 제거로 해결하지 않는다.
- 현재 metadata 3행/10테이블 보존과 최신 기준 재결속을 함께 확인한다. 서로 다른 배치의 오래된 baseline으로 최신 서지·다른 작품 판정을 소실시키지 않는다.
- 기존 東京喰種·月と指先の間의 봉인 PASS를 재사용해 대표 publish 흐름을 확인한다. 유효한 판정을 다시 만들지 않는다. 불완전 publication 디렉터리는 실패 이력으로 남기고 기존 재개/새 시도 경계를 사용한다.
- ジャイアントお嬢様의 CP949 stdout 실패는 기존 subprocess 경계의 UTF-8 적용으로 해결한다. 이미 저장된 HOLD를 재판정하지 않는다.
- 수용: 변경 후 같은 발행 경로의 성공·DB readback·백업과 alias 삭제/무단 추가 거부를 확인한다. 이 계획 작성에서는 해당 코드 수정·발행을 실행하지 않았다.

### P1. runner에서 비발행 준비·검사 분리

- 대상: `scripts/catalog_authoring_runner.py`, `prepare_factor_batch.py`, `factor_single_pass.py` 및 기존 테스트.
- 현재 `run --decisions`는 검사 뒤 즉시 publish/STATE 갱신을 한다. worker에 이 명령을 ‘검사만’이라고 배정하지 않는다. `finish`도 내부 발행 단계다.
- 기존 runner에 모델 호출 없이 **prepare**와 **check** 단계 진입점을 추가하는 안을 사용한다. 이름은 설계안이며 구현 전 명령 예제로 실행하지 않는다. prepare는 기존 job 조립·ensure_frozen·읽기 view/schema 준비, check는 기존 hold_result·seal_result·재사용 검사를 공유한다. 새 독립 validator나 병렬 파이프라인을 만들지 않는다.
- check는 비발행 receipt를 남기고 공유 candidate/registry/STATE·canonical을 변경하지 않는다. HOLD를 일반 seal_result에 억지로 전달하지 않는다.
- 조정자의 기존 run 후처리는 같은 SHA로 봉인된 결과를 재사용한다. 기존 --decisions 기본 동작과 명시적 --allow-model 경계를 보존한다. 배치 작업은 모델 호출 옵션을 켜지 않는다.
- 수용: prepare/check의 실제 CLI에서 후보·STATE 불변, PASS/HOLD/ERROR별 저장, 입력 변경/변조 거부, 중복 재개 시 모델·봉인 재실행 없음. 모델이 만든 실제 결과를 주 경로로 발행한 증거와 mock 단위 테스트를 구분한다.

### P2. 배정 인덱스·작품별 brief와 배치 통지

- 기존 DISPATCH/RUN/receipt를 참조하는 작은 배치 목록과 진행 집계를 추가한다. 새 DB·daemon·예약 automation을 만들지 않는다. 조정자만 배정 소유권을 쓰고 작업자는 자기 배치의 완료/오류 기록을 쓴다.
- 작품별 brief는 정확한 workId·대표 ISBN/권·근거/prior/HOLD·raw/receipt·리드 경로와 해결할 gap을 포함한다. 코드/계약은 세션 시작 때 한 번 읽고 버전이 바뀌면 변경분을 다시 확인한다. 의미 근거를 줄이는 임의 토큰 상한은 두지 않는다.
- 세션 누적 문맥이 커지면 artifact checkpoint로 이어간다. 압축/턴 종료 뒤에는 현재 작품의 동결 경계를 재확인하며 새 세션 생성으로 자동 우회하지 않는다. 이미 배정된 목록 안의 다음 작품은 새 조정자 승인 없이 진행한다.
- 기존 `notification_guard.py`는 `len(works)==1`과 workId를 요구한다. batchId를 가짜 workId로 넣지 않는다. 배치 모드를 추가해 배정 목록과 최종 결과 집합·SHA·부모 수신 성공을 확인하고 기존 단일 작품 모드를 보존한다.
- 배치 통지 설계: `CATALOG_BATCH_COMPLETE: batchId=...; summaryPath=...; sha256=...`. 결과 전달 실패는 결과를 보존해 통지/ack만 재개한다. summaryPath/SHA만으로 승격을 허용하지 않고 수신 측은 작품별 결속을 코드로 확인한다.
- 배치 완료 전 중단·공통 오류·쿼터 소진은 부분 완료 통지를 보낸다. 100개가 될 때까지 오류를 감추거나 사용자의 중단을 무시하지 않는다. 마지막 묶음도 전체 배정 수로 완료 판정한다. 전체 완료 후 새 묶음은 조정자가 배정한다.
- 수용: 3개 목록 중복 거부, 통지 누락·중복 수신·중간 종료·부분 재개·작품 중복 발행 방지. 실제 고정 세션에서 배치 통지 수신을 확인하며 함수 테스트만으로 훅이 작동한다고 보고하지 않는다.

### P3. 발행 주기와 병목 계측

- 한 배치 완료마다 조정자 한 번의 처리 주기로 유효 결과를 직렬 발행한다. 초기에는 기존 작품별 build/readback을 유지한다. 조정자 호출을 줄였다는 이유로 제품 검사를 생략하지 않는다.
- 발행 단계가 실제 병목이면 기존 bulk 지원과 저장 계약을 확인해 build/readback을 배치 수준으로 묶는 변경을 별도 구현한다. 여러 작품의 판정 파일을 새 입력으로 합쳐 원래 manifest를 잃는 우회는 금지한다. 지원되기 전 ‘100개당 build 한 번’이라고 주장하지 않는다.
- 한 배치가 발행 중이어도 다른 세션은 자기 분리된 입력·출력에서 작업할 수 있다. 모든 writer는 기존 잠금을 지키며 대량 모델/네트워크 대기에 publication 잠금을 잡지 않는다.

### P4. 시작 점검과 첫 배치군

P0~P2가 실제 경로에서 확인되고 세션 ID·재개 지시가 준비되면 기존 3작품 결과로 경계 검증을 마친 뒤 3개 묶음을 배정한다. 처음부터 300작품을 처리해봐야 구현 결함을 알 수 있는 구조로 만들지 않는다. 검증은 소수의 실제 아티팩트로 끝내고 반복 비교용 모델 호출을 추가하지 않는다.

첫 배치군은 동일 기준으로 측정해 유지·수정 여부를 결정한다. 품질 문제가 없다면 계속 같은 세션으로 다음 묶음을 처리한다. 과거 Luna 결과와 비교할 때 원문 확보 상태·HOLD 유형·난도별로 나누며, 명확한 차이가 없으면 추가 동시 Luna 실험 없이 효과 미확인으로 보고한다.

## 9. 계측과 비교 방법

작품별 기존 기록에 배정, 조사 시작/끝, 저장·동결 시작/끝, 최초 판정 저장, 수정별 검사, READY/HOLD/ERROR 확정, 발행 시작/끝, readback·backup 완료 시각을 남긴다. 전체 경과시간과 하위 구간이 겹치면 합산하지 않는다. 이전 수집시간과 이번 추가 작업시간을 분리한다.

토큰은 실제 누적 usage 차분으로 input/cached input/output을 기록하고 추론을 출력에 중복 합산하지 않는다. 작업자와 조정자를 합산하되 배정·표본 검토·진단·보고 비용도 포함한다. 다른 세션이나 이전 중단 시간은 섞지 않는다. 노출되지 않는 값은 unavailable이며 캐시율/과금 추정치로 채우지 않는다.

| 지표             | 산식·해석                                                                  |
| ---------------- | -------------------------------------------------------------------------- |
| 유효 PASS 비율   | 기계 검사 통과 READY / 판정 완료 수. 알려진 의미 오류는 별도 보고          |
| 최종 승격률      | VERIFIED / 배정 수. HOLD·오류·미완료 분모를 숨기지 않음                    |
| 시간당 승격      | 세션군 첫 작업 시작부터 readback·backup 종료까지의 실제 경과시간 기준      |
| 승격당 사용량    | 작업자 + 조정자 + 실패/재조사 토큰 / VERIFIED. 0건이면 계산 불가            |
| 검색 확장의 효과 | 추가 검색으로 해결된 gap·실제 승격과 그 비용, 이후 재배정 감소를 함께 기록 |
| 지연             | 작품 READY부터 배치 발행까지 대기시간. 100개 묶음의 단점도 측정            |

계획용 계산: 3세션에서 작품당 평균 t분, 최종 발행 가능 비율 p라면 작업자 공급 상한은 대략 `180 × p / t`건/시간이다. 실제 처리량은 직렬 발행 속도와 운영비용에 제한된다. 예를 들어 t=8, p=0.6이면 13.5건/시간이지만 이는 가정이며 실측 예측이 아니다. 높은 PASS가 더 긴 탐색·재작업·큰 입력을 상쇄하는지는 첫 배치 결과로 판단한다.

## 11. 2026-09-21 연속 실행 승인 및 구현 현황

사용자는 Sol이 수집·판정·비발행 검사, Astra가 배치 확인·직렬 승격을 맡아 중단 없이 계속하도록 승인했다. 예약 automation 없이 고정 세션의 완료/부분 보고를 재개 신호로 사용한다. 임의 응답 예산 판단은 종료 사유가 아니며 실제 오류·사용자 중단만 부분 종료 사유로 구분한다.

runner `prepare/check`와 `CHECKED.json`·`CHECK-STORAGE.json`, notification_guard `register-batch`가 구현됐다. [runner 명령 계약](../../scripts/catalog_authoring/README.md)을 따른다. 이전 절의 ‘구현 전’은 계획 시점 기록이다. 실제 東京喰種 판정을 재사용한 check 및 후보 발행·SQL/build/coverage/추천 엔진 readback을 통과했다. 후보 추천 가능 수는 두 작품 복구 후 1,826→1,828이며 canonical은 별도 반영 전이다. Gold alias는 최초/부분/완료 delta와 무단 변경을 구별하고, 후보 서지는 canonical metadata를 보존한다.

수집 100건은 판정 PASS 100건이 아니다. 개별 collection remainingGaps가 남아 있으면 같은 Sol이 판정 전 해당 gap을 해결하거나 출처 소진 근거를 남긴다. 작품별 원문/관찰을 재검토하는 정상 단계에 조정자 왕복을 추가하지 않는다.

검증 한계: 기존 test_prepare_factor_batch 전체에는 사라진 jobs/hina-drifters/records.json 및 과거 frozen canonicalSha256 불일치로 실패하는 artifact 검사가 있다. 새 alias/metadata 회귀, runner 28개, notification guard 2개와 실제 현재 경로의 prepare/check 및 두 후보 발행을 별도로 확인했다. 오래된 fixture 실패를 이번 변경의 PASS로 보고하지 않는다.

첫 실제 배치에서 확인한 수집 누락: v3 packet의 contextEvidenceId=null은 정상 미판정 계약이다. supplemental sourceUrl과 registry supportEvidenceUrls가 겹치지 않아 context enum이 빈 문자열만 허용한 작품이 있었다. 작업자는 지정 추천/선정 URL의 실제 작품 근거를 추가 수집한 새 revision으로 이어가며, validator를 완화하거나 전체 배치를 중단하지 않는다.


## 12. 사용자 정정 — 수집 배치와 판정 배치를 분리

100작품의 자료 확보·gap 보완을 먼저 완료하고, 이후 같은 세션이 작품별 frozen 입력으로 판정을 연속 처리한다. 수집된 한 작품을 곧바로 판정한 뒤 다음 작품을 수집하는 교차 운영은 폐기한다. 독립 수집 요청을 묶고 공통 원문을 재사용해 반복 비용을 줄이되, 100작품을 하나의 거대한 모델 입력/판정 파일로 합치지는 않는다. 각 작품의 입력·저장·무결성 검사는 유지한다. 수집 완료 시 추가 근거가 충분한 작품과 출처 소진 INSUFFICIENT를 구분하며, 후자를 조사만으로 PASS시키지 않는다.

Sol 1·2·3에 새 판정 시작을 보류하고 전체 수집·보완을 먼저 마치도록 정정 지시했다. 이미 만든 판정과 실패 이력은 보존한다. Sol 3의 기존 100건 EVIDENCE_FOUND 보고에도 remainingGaps 및 추천 맥락 source 누락이 있어 보완 완료와 구별한다.


## 13. 작업자 관측에 따른 수집 효율화

Sol 2·3의 실제 보고를 반영했다. 배치별 COLLECTION-CONTEXT.json에 dispatch/registry SHA, 작품별 supportEvidenceUrls·sourceFamilies·cohortKeys union과 원 registry 행을 저장한다. 이번 300작품은 322개 registry 행이며 세 방의 고유 support URL은 각각 46/49/40개다. lookup은 수집 리드이며 source 권한이 아니고, registry 변경 시 재결속한다. 기존 dispatch는 변경하지 않는다. 제공 URL과 support URL은 중복 제거 후 같은 요청으로 묶고 이미 확보한 공통 raw/receipt를 재사용하되 작품 연결·scope·readAudit를 유지한다.

validator는 collection 전체와 실행 helper를 실행 전에 workspace에 저장·백업한다. 실제 receipt가 동일 bytes의 저장과 BACKED_UP을 확인하고 파일이 변하지 않았으면 중복 collection 전체 save를 생략한다. 이후 변경된 REPORT/progress/summary와 바깥의 새 원문은 별도로 저장한다. 배치 고정 dispatch·user-source·helper는 snapshot 6965에 보존했다. 작품별 필수 백업을 배치 끝으로 미루지는 않는다. Sol 3이 보고한 백업 교체 WinError 32는 원인 확인 대상으로 남기며 백업 빈도를 낮춰 은폐하지 않는다.


## 14. Sol 3 첫 판정 배치 반려

HOLD 56/ERROR 44/READY 0 보고를 그대로 수용하지 않았다. 실행 로그에서 첫 작품을 제외한 55개 준비 결과에 반복문으로 동일 서지 부족 HOLD를 작성한 것을 확인했다. 이는 의미 판정을 코드 기본값으로 대체한 HARNESS SUBSTITUTION이며 판정 완료로 인정하지 않는다. 원본 summary·판정은 보존하고 작품별 frozen 근거를 실제로 읽은 새 판정을 요구했다. ERROR 39건은 조정자 배정에서 복구 경로가 누락된 것이며 기존 검증된 epoch의 authority-unresolved membership을 확인해 명시적 복구 경로를 제공했다. 나머지 5건은 registry의 alternate-volume 증거 오류로 구분했다. BATCH-REVIEW-RETURN.json과 원 보고는 snapshot 7393에 저장·백업했다. 유효 HOLD를 낮추기 위한 기준 완화는 하지 않는다.
