## 1. 보존할 강점 [KEEP]

다음은 이 계획서의 핵심 자산이며 수정 없이 유지한다.

- **제품 가설 A~E와 12개 제품 원칙.** 특히 "데이터 없음 ≠ 불호", "설명은 실제 점수 기여에서 생성", "런타임 LLM이 순위를 결정하지 않음", "시장 신호는 tie-break"는 이 제품의 정체성 그 자체다.
- **Best Anchor + 제한된 Consensus Bonus.** Top-3 합산 폐기는 소수 취향 보존 문제를 정확히 짚은 좋은 결정이다.
- **부정 신호의 3단 분리** (Hard Exclusion / Factor Penalty / Vague Shape Penalty) + 외부적 하차 이유의 감점 제외.
- **unknown / notApplicable / Coverage 중립 수축.** "결측 그룹의 가중치를 다른 그룹에 재분배하지 않는다"는 규칙은 흔히 놓치는 함정을 정확히 막는다.
- **팩터 범위를 초반 1~3권으로 고정.** Late-volume bias에 대한 올바르고 저렴한 해법.
- **Work / Volume / ProviderListing 분리와 Rakuten 캐시 TTL 준수.** 법적·기술적으로 모두 옳다.
- **로컬 우선(회원가입 없음, Dexie, Export/Import) 아키텍처.** MVP 가설 검증에 서버 사용자 데이터가 불필요하다는 판단은 정확하다.
- **"UI보다 Catalog와 Scorer를 먼저 검증한다"는 순서 감각.** (실행 방법은 아래에서 수정함)
- **konomi 로고 기믹.** 제품 컨셉(숨은 취향의 발견)과 브랜드가 구조적으로 일치하는 드문 사례. 비주얼 시스템 전체를 이것을 중심으로 세울 가치가 있다.

## 2. 발견 사항

### P-1. [MUST] 온보딩이 과도하게 길다 — 사전 질문과 사후 보정의 중복

현재 흐름: 좋아한 작품 5~8개 → 싫어한 작품 0~3개 → **중요 요소 최대 3개 → 회피 요소 최대 3개** → DNA 확인·보정 → 추천.

"중요 요소/회피 요소" 사전 선택(4~5단계)은 DNA 보정 단계(6단계)와 기능이 중복된다. 스코어링 영향도 작다(계획서 스스로 그룹 비중 ±5%p로 제한). 추천을 보기 전에 추상적 질문("작화가 중요합니까?")에 답하게 하는 것은, 추론된 DNA를 보여주고 고치게 하는 것보다 UX·데이터 품질 모두 나쁘다.

→ 사전 요소 선택 2단계를 제거하고 DNA reveal 화면의 인라인 보정으로 병합. 온보딩은 "작품 선택 → (선택) 불호 작품+이유 → DNA reveal & 보정 → 추천" 3.5단계가 된다.

### P-2. [MUST] 재방문 사용자와 라우팅 상태가 미정의

계획서는 신규 사용자 흐름만 정의한다. 다음이 비어 있다:

- 프로필이 있는 사용자가 `/`에 오면? → 결정: `/recommendations`로 클라이언트 리다이렉트.
- Anchor가 5개 미만인 중단 상태로 이탈했다가 돌아오면? → 온보딩 진행 상태를 Dexie에 저장하고 이어서 진행.
- 추천은 언제 재계산되는가? (읽음 처리 후? 페이지 진입 시?) → 계약 필요. `03-ux-screen-contracts.md` §5에서 확정.

### P-3. [SHOULD] `/taste` 화면과 `/settings`의 "취향 보정" 중복

취향 보정 UI가 두 곳에 존재한다. → 취향 보정은 `/taste` 단독 소유. `/settings`는 추천 정책·데이터 관리만.

### P-4. [SHOULD] "이번 추천에만 반영하는 Mood" 기능은 시기상조

전역 취향/현재 Mood 분리는 좋은 장기 아이디어지만, MVP 가설(A~E) 어느 것도 검증하지 않으면서 상태 모델·UI·설명 로직을 복잡하게 만든다. → DEFER.

### P-5. [SHOULD] 추천 정책 6종은 MVP에 과다

"검증된 작품 우선 / 신작 탐색 / 완결 우선 / 장편 우선 / 숨은 작품 우선 / 정확 일치 우선" 6종 중 다수가 tie-break 순서만 바꾸는 미세 조정이고, 각각이 설명·테스트 비용을 만든다. → MVP는 3종(완결작 우선, 숨은 작품 우선, 검증된 작품 우선)으로 축소. 나머지는 DEFER.

### R-1. [MUST] Spreadsheet 수식 검증(Phase 1)은 실행 불가능에 가깝다

Best Anchor 선택, presence-sensitive 거리, Coverage 중립 수축, notApplicable 분모 제외, 사유별 Penalty Cap을 Google Sheets 수식으로 구현하는 것은 TypeScript로 구현하는 것보다 **더 오래 걸리고 더 오류가 많다**. 스프레드시트 버전과 TS 버전의 불일치를 디버깅하는 이중 비용도 생긴다.

→ REPLACE: 스프레드시트는 **주석(annotation) 입력 도구**로만 사용하고, 계산은 처음부터 TypeScript 엔진 + CLI 리포트로 수행한다. 검증하려던 것(이상한 Top 10, 소수 취향 소멸, unknown 과대평가)은 CLI 출력으로 동일하게 확인 가능하며, 이 엔진 코드가 그대로 블라인드 테스트와 프로덕션에 재사용된다.

### R-2. [MUST] `explicitPreferenceAdjustment`가 수식 없이 점수식에 등장한다

25장 점수식에 항이 있으나 크기·조건·상한이 어디에도 정의되지 않았다. 구현 모델이 임의로 정하게 되는 대표적 fork. → `02-product-spec.md` §6.6에서 수치 확정 (per-axis ±0.03/±0.06, 총합 ±0.12 cap).

### R-3. [MUST] 불호·하차 이유의 어휘와 팩터 매핑이 예시 4개뿐

Factor-specific Penalty는 이 엔진의 핵심 차별점인데 "너무 느림 → pacing" 등 예시만 있다. 고정 enum과 전체 매핑 테이블 없이는 UI·엔진·설명이 모두 구현 불가. → `02-product-spec.md` §6.7에서 12개 사유의 고정 어휘와 매핑을 확정.

### R-4. [SHOULD] `profileConfidence` 수식이 부정 입력 없는 사용자를 과소평가

부정 이유가 가중치 30%라서, 불호 작품을 입력하지 않은(정상적인) 사용자는 Anchor를 8개 채워도 confidence 0.7에 머문다. 부정 입력은 선택 사항이므로 비중을 낮춘다. → `0.8 × min(anchor/8,1) + 0.2 × min(reasonedNeg/2,1)`로 조정.

### R-5. [KEEP] 17개 Axis의 규모는 유지하되, Phase 1 데이터로 병합 후보를 진단

`visualSoftness`↔`artRealism`, `problemSolving`↔`strategy`는 상관이 높을 수 있으나, "세부 취향이 가치 있다"가 검증 대상 가설 그 자체이므로 선험적으로 줄이지 않는다. 50작품 주석 후 상관계수 리포트(`catalog:coverage`)로 병합 여부를 데이터로 판단한다. 팩터 사전은 버전 관리한다.

### A-1. [MUST] Next.js 클라이언트/서버 경계가 선언되지 않아 구현 fork가 크다

"Next.js App Router"만 명시하면 구현 모델은 RSC 데이터 페칭, 서버 액션, SSR 하이드레이션 전략을 각자 판단하게 된다. 이 앱의 상태 원천은 브라우저(Dexie)이므로 서버 렌더링할 사용자 데이터가 없다.

→ 경계 선언: **모든 페이지는 정적 프리렌더된 셸 + 클라이언트 컴포넌트. 서버 코드는 `/api/rakuten/*` Route Handler 단 하나. 서버 액션·RSC 데이터 페칭·동적 SSR 금지.** (`05-architecture.md` §3)

### A-2. [MUST] Library-only Rakuten 검색의 런타임 Work 그룹핑 문제

Work 자동 그룹핑(12장)은 빌드 파이프라인 설계인데, Library 검색은 런타임에 라쿠텐 **권(Volume)** 결과를 받는다. 런타임에 어떻게 Work로 만드는지 미정의.

→ 결정: 검색 결과를 ISBN으로 Catalog와 대조하여 일치하면 Catalog Work에 연결, 불일치하면 정규화된 제목+저자 키의 **외부 항목(external entry)** 으로 저장. 외부 항목은 추천·DNA 계산에 절대 사용하지 않고 Library 기록·Export에만 존재한다. 그룹핑 정확도는 보장하지 않음을 명시.

### A-3. [SHOULD] Export/Import 스키마가 미정의

"Export/Import 가능"만 있고 포맷·버전·부분 실패 처리가 없다. → v1 스키마(zod), 전체 트랜잭션 적용(부분 적용 금지), 미래 major 버전 거부를 `05-architecture.md` §7에서 확정.

### A-4. [SHOULD] NDL Search는 MVP 경로에 없다

NDL은 빌드 파이프라인 보조인데 "현재 사용" 서비스로 분류되어 있다. 150개 수동 검수 Catalog에서 서지 충돌은 사람이 직접 확인하는 편이 빠르다. → MVP에서 완전 제외(DEFER). Rakuten 데이터 품질 문제가 실제로 발생하면 도입.

### A-5. [KEEP] Netlify Free / 정적 Catalog / Dexie / Route Handler Proxy

2026-08 기준 검증: Netlify Free는 월 300 크레딧 하드 리밋(초과 시 일시 정지, 과금 없음), Next.js Runtime v5 공식 지원. 계획서의 전제와 일치한다.

### V-1. [MUST] Aurora/Dot Grid WebGL 배경은 브랜드와 무관한 범용 장식이다

Aurora는 2024~26년 AI/SaaS 랜딩의 클리셰이며, KonoComics의 어떤 제품 개념(만화, 인쇄, 취향, 발견)도 강화하지 않는다. WebGL 상시 렌더링은 모바일 배터리·저사양 기기 비용도 크다.

→ REPLACE: **스크린톤(망점) 텍스처.** 만화 인쇄 문화의 시각 언어를 CSS `radial-gradient` 정적 패턴으로 구현한다. 브랜드 적합성은 높아지고 런타임 비용은 0이 된다. (`04-visual-interaction-spec.md` §3.4)

### V-2. [MUST] React Bits 의존성은 제거 가능하고 제거해야 한다

계획서가 채택 후보로 든 5개 컴포넌트를 개별 평가하면:

| 후보 | 판단 |
|---|---|
| Aurora / Dot Grid | V-1에서 대체 |
| Stack / Card Swap | Motion으로 ~50줄 자작 가능 (landing 표지 팬) |
| Animated Content | Motion 기본 기능 |
| Spotlight Card | 피드는 조용해야 함 — 효과 자체를 제거 |
| Tilted Card | 3D tilt는 의미 없는 장식 — 제거 |

남는 실사용처가 없다. 라이선스(MIT+Commons Clause, 사용 가능함은 확인됨) 추적 문서, 소스 복사 관리, 스타일 이질성 비용만 남는다. → REMOVE. 필요 효과는 Motion + CSS로 자작.

### V-3. [SHOULD] NumberFlow는 잘못된 정밀도 신호를 만든다

Manga DNA의 축 값은 0~4의 서수(질적 단계)이고 계획서 스스로 "확률로 표시하지 않는다"고 정했다. 숫자 굴림 애니메이션은 정밀 측정값의 시각 언어라서 원칙과 충돌한다. → REMOVE. DNA reveal은 막대 성장 애니메이션 + 레이블로 표현.

### V-4. [SHOULD] Embla·AutoAnimate는 플랫폼 기본 기능으로 충분

- 장르별 Shelf: CSS scroll-snap(`overflow-x` + `scroll-snap-type`) + 이전/다음 버튼으로 구현 가능. 자동재생·루프가 없으므로 Embla의 부가가치가 없다. → REMOVE.
- Library 목록 추가/삭제: Motion `layout` 애니메이션으로 커버. AutoAnimate 불필요. → REMOVE.

이로써 시각 관련 외부 의존성은 **Motion 하나**가 된다.

### V-5. [MUST] 표지 200×200 전제는 사실이 아니며, 비주얼 설계를 바꾼다

검증 결과: 라쿠텐 이미지 URL의 `_ex` 쿼리 파라미터를 수정하면 더 큰 해상도를 받을 수 있다(예: `_ex=400x400`, `_ex=600x600`). 공식 문서가 보장하는 필드는 200×200까지이므로, **프록시에서 `_ex`를 재작성하되 로드 실패 시 200×200으로 폴백**한다. 이로써 작품 상세의 대형 표지 표현이 실제로 가능해진다.

### V-6. [SHOULD] 다크 모드가 언급조차 없다

만화 독자는 야간 사용 비중이 높다. 단, 검증 단계에서 두 테마의 시각 QA는 과잉이다. → 시맨틱 토큰은 첫날부터 설계하고, MVP 검증 단계는 라이트("종이와 잉크") 단일 테마, 다크 모드는 폴리시 슬라이스에서 정식 추가.

### S-1. [SHOULD] Phase 0~6이 7단계로 쪼개져 있고 블라인드 테스트 도구가 미정의

R-1의 결정(엔진 즉시 TS 구현)에 따라 Phase 0/1/2가 자연 병합된다. 또한 Phase 3 블라인드 테스트를 "어떻게" 진행하는지(참가자에게 무엇을 보여주고 어떻게 기록하는지)가 없다. → 5단계로 재편, 블라인드 테스트는 엔진·Catalog를 재사용하는 최소 로컬 웹 하니스로 진행. (`06-implementation-plan.md` §1)

### S-2. [KEEP] "엔진 검증 GO 전에 프로덕션 UI에 투자하지 않는다"

핵심 순서 원칙은 옳다. 단, 디자인 토큰·화면 계약(본 문서 세트)은 병렬로 확정해 두었으므로, GO 판정 후 UI 구현이 병목 없이 시작된다.

## 3. 리스크 요약 (변경 없이 재확인)

1. **최대 리스크는 여전히 데이터 생성 비용이다.** 150작품 × (17 Axis + Theme + Genre + 근거) 수동 주석이 임계 경로다. 계획서의 대응(범위 축소, 추천 상위 우선 검수, Library-only 강등)은 유효하며 유지한다.
2. **"설명은 맞는데 읽고 싶지 않다" 실패 모드** — 계획서 43.6의 진단 순서(엔진 폐기 전에 Catalog Hook·진입성 점검)를 유지한다.
3. **상표/도메인 미확인** — 사용자 소유 결정. 공개 전 J-PlatPat·핸들 확인 필요(계획서 2.6). 내부 개발명으로는 즉시 사용.
